# Частина 1. Розгортання

## 1. Підготовка Windows

### 1.1 MS SQL Server — увімкнути змішану автентифікацію

Docker-контейнер підключається до SQL Server, який стоїть прямо на цьому ж комп'ютері (Windows), логіном і паролем — не через Windows-автентифікацію (вона з Docker не працює). Тому потрібно:

1. Відкрити **SQL Server Management Studio (SSMS)**.
2. Підключитися до локального сервера.
3. Правою кнопкою на імені сервера (вгорі в "Object Explorer") → **Properties**.
4. Зліва обрати вкладку **Security**.
5. У розділі "Server authentication" обрати **SQL Server and Windows Authentication mode**.
6. Натиснути **OK**.
7. Правою кнопкою на сервері → **Restart** (без перезапуску зміна не набуде чинності).

### 1.2 Створити користувача бази даних для проекту

У SSMS відкрити **New Query** і виконати:

```sql
CREATE LOGIN mm_user WITH PASSWORD = 'mmNextRetail_TS-2026';
USE original;
CREATE USER mm_user FOR LOGIN mm_user;
ALTER ROLE db_owner ADD MEMBER mm_user;
```

> Пояснення: `original` — назва бази даних кіоску (якщо її ще немає — спочатку створіть порожню базу з такою назвою через SSMS: правою кнопкою на "Databases" → **New Database** → ім'я `original`). Роль `db_owner` потрібна, бо при першому запуску бекенд сам створює всі таблиці.

Пароль `mmNextRetail_TS-2026` — той самий, що вже прописаний у `docker-compose.yml` у рядку `DATABASE_URL`. Якщо хочете інший пароль — заміните його одразу в обох місцях (тут і в `docker-compose.yml`).

### 1.3 Git (для отримання коду проекту)

Якщо на комп'ютері ще немає Git — встановити з https://git-scm.com/download/win (варіанти установки залишити за замовчуванням).

## 2. Встановлення Docker Desktop

Весь кіоск (бекенд + фронтенд) запускається всередині Docker — окремих Node.js/npm встановлювати не потрібно.

1. Завантажити **Docker Desktop for Windows**: https://www.docker.com/products/docker-desktop/
2. Запустити інсталятор, залишити налаштування за замовчуванням.
3. Комп'ютер попросить перезавантаження — погодитись.
4. Після перезавантаження запуститься Docker Desktop, попросить прийняти умови ліцензії — прийняти.
5. Якщо Docker Desktop повідомить про необхідність увімкнути **WSL2** — натиснути на посилання у вікні й виконати запропоновані кроки (зазвичай це один `wsl --install` у PowerShell від імені адміністратора й ще одне перезавантаження).
6. Коли Docker Desktop відкрився і показує "Engine running" (зелений індикатор внизу зліва) — усе готово.
7. **Settings** (шестерня вгорі) → **General** → увімкнути **Start Docker Desktop when you log in**. Це важливо: якщо цю опцію не увімкнути, після перезавантаження комп'ютера/збою електроенергії кіоск сам не підніметься.

## 3. Отримання проекту та перший запуск

### 3.1 Клонування репозиторіїв

Відкрити **Git Bash** (встановився разом з Git) або PowerShell:

```bash
cd C:/git
git clone https://github.com/OlehBrov/mm-back-ts.git mm-back-nest
git clone https://github.com/OlehBrov/mm-front-ts.git mm-front-ts
git clone https://github.com/OlehBrov/mm-deploy.git mm-deploy
mkdir C:/git/mm-images
```

Отримаємо структуру:
```
C:/git/mm-back-nest   — бекенд (сервер)
C:/git/mm-front-ts    — фронтенд (екран кіоску)
C:/git/mm-deploy      — docker-compose.yml (керує запуском обох)
C:/git/mm-images      — сюди зберігатимуться фото товарів/категорій (спільна папка з контейнером)
```

### 3.2 Перевірити/налаштувати `docker-compose.yml`

Відкрити `C:/git/mm-deploy/docker-compose.yml` будь-яким текстовим редактором (Notepad, VS Code). Це файл, де прописані **всі** налаштування, потрібні для запуску — не потрібно створювати окремий `.env`.

Ключові рядки, які варто перевірити/змінити під конкретний кіоск:

| Рядок | Що це |
|---|---|
| `DATABASE_URL` | Рядок підключення до SQL Server. Міняти лише якщо змінили пароль `mm_user` у кроці 1.2 |
| `CLIENT_HOST` | IP-адреса POS-терміналу в локальній мережі кіоску (з'ясувати заздалегідь, бажано зробити статичною) |
| `CLIENT_PORT` | Порт терміналу: `3000` для MonoBank, `2000` для PrivatBank |
| `TERMINAL_PROVIDER` | `monobank` або `privatbank` — початковий банк (можна змінити пізніше через екран конфігу) |
| `STORE_ID`, `STORE_AUTH_ID` | Ідентифікатори конкретного магазину. `STORE_AUTH_ID` — логін для входу у фронтенд-адмінку |
| `MAIL_HOST` ... `MAIL_SUPPORT_PASS` | SMTP-акаунт(и) для листів (детальніше — [розділ 9](#9-автоматичні-звіти)) |
| `VITE_STORE_LOGIN`, `VITE_STORE_PASSWORD` | Логін/пароль для входу в кіоск (build args фронтенду) |
| `VITE_CONFIG_BARCODE` | Спеціальний штрихкод, скан якого відкриває екран конфігу (див. [розділ 6](#6-екран-конфігу)) |

> Нічого з переліченого змінювати НЕ обов'язково для першого запуску — усе вже має робочі значення. Змінюйте лише те, що дійсно відрізняється для вашого кіоску (IP терміналу — обов'язково).

### 3.3 Перший запуск

```bash
cd C:/git/mm-deploy
docker compose up --build -d
```

Перший запуск триває кілька хвилин (завантажуються базові образи, збирається код). Перевірити статус:

```bash
docker compose ps
```

Мають бути два контейнери зі статусом `Up`: `backend` і `frontend`.

Перевірити логи бекенду:
```bash
docker compose logs backend --tail=80
```

При успішному старті побачите:
```
[Migrations] Applied: 001_add_fiscal_queue.sql
...
[Migrations] Applied: 024_add_mail_config.sql
[NestApplication] Nest application successfully started
Application running on port 6006
```

Якщо в логах є рядки `ERROR` — див. [розділ 11 «Усунення несправностей»](#11-усунення-несправностей).

### 3.4 Перевірити, що фронтенд відкривається

Відкрити в браузері на цьому ж комп'ютері: **http://localhost**

Побачите або екран логіну (якщо кіоск уже частково налаштований), або автоматичний перехід на екран **"Введіть пароль"** → **"Налаштування кіоску"** — це нормально, якщо кіоск ще не налаштований (див. [розділ 6](#6-екран-конфігу) — пароль за замовчуванням береться з таблиці `ServiceUsers`, стандартний **`123456`**).

### 3.5 Логін у фронтенд (пароль магазину)

Пароль для входу в сам кіоск (не плутати з паролем екрана конфігу!) задається build-аргументом `VITE_STORE_PASSWORD` у `docker-compose.yml` і зберігається в БД як bcrypt-хеш у таблиці `Store`. Щоб змінити пароль пізніше без перезбірки фронтенду:

```bash
docker exec mm-deploy-backend-1 node -e "const b=require('bcryptjs'); b.hash('НОВИЙ_ПАРОЛЬ',10).then(h=>console.log(h))"
```

Скопіювати результат (рядок, що починається з `$2b$10$...`) і виконати в SSMS:

```sql
UPDATE dbo.Store SET password = '$2b$10$...' WHERE auth_id = '998877';
```

(`998877` — значення `STORE_AUTH_ID`; якщо в вас інше — підставити своє.)

### 3.6 Заповнити конфіг кіоску

Найпростіший спосіб — через сам кіоск: див. [розділ 6](#6-екран-конфігу) (екран **"Налаштування кіоску"**, `http://localhost/#/setup`). Там покроково: назва/адреса магазину, вибір банку-термінала, IP/порт терміналу, перевірка зв'язку, призначення мерчантів, токени Вчасно.Каса.

Альтернатива — напряму через API одним запитом, див. [розділ 14.4](#post-apisetupkiosk-config).

### 3.7 Завантажити товари й категорії

Товари й категорії зазвичай завантажуються автоматично із зовнішньої системи (1С) через API (`POST /api/products/add`, `POST /api/config/category`, `POST /api/config/subcategory` — див. [розділ 15](#15-products) і [17](#17-config)). Якщо інтеграції з 1С немає — товари можна додати вручну тими самими запитами (наприклад, через Postman).

## 4. Автозапуск при вмиканні комп'ютера

Кіоск повинен самостійно піднятися після перезавантаження ПК або збою електроенергії — без участі людини.

### 4.1 Docker-контейнери

Уже налаштовано в `docker-compose.yml` (`restart: unless-stopped`) — після старту Docker Desktop контейнери піднімуться самі, якщо Docker Desktop сам налаштовано на автозапуск (крок 2.7 вище).

### 4.2 Chrome в режимі кіоску

**Планувальник завдань Windows (Task Scheduler) → Create Task:**

- **General:** ім'я `MM Kiosk`, галочка ✅ **Run with highest privileges**
- **Triggers → New:** **At log on**, Delay task for: **1 minute** (щоб Docker встиг піднятись)
- **Actions → New:** Program/script: `powershell.exe`; Arguments: `-ExecutionPolicy Bypass -WindowStyle Hidden -File "C:\git\mm-deploy\start-kiosk.ps1"`
- **Settings:** зняти "Stop the task if it runs longer than..."; галочка "If the task is already running, do not start a new instance"

Скрипт `start-kiosk.ps1` (лежить у `mm-deploy`) кожну секунду перевіряє доступність `http://localhost` до 2 хвилин, потім відкриває Chrome командою `chrome.exe --kiosk --no-first-run http://localhost` (повноекранний режим без адресного рядка, без можливості вийти звичайними засобами браузера).

### 4.3 Windows — автологін (опційно)

Якщо кіоск має підніматись повністю без людини навіть після переривання живлення, налаштуйте автоматичний вхід у Windows під обліковим записом, з-під якого запущено Task Scheduler-завдання (Панель керування → Облікові записи, або утиліта `netplwiz`).

# Частина 2. Як працює кіоск (для підтримки)

## 5. Архітектура простими словами

```
┌─────────────┐   HTTP/WebSocket    ┌──────────────┐    TCP     ┌───────────────┐
│  Фронтенд   │ ──────────────────► │   Бекенд     │ ─────────► │  POS-термінал  │
│  (браузер   │ ◄────────────────── │  (NestJS,    │ ◄───────── │ (MonoBank або  │
│  у режимі   │                     │   порт 6006) │            │  PrivatBank)   │
│  кіоску)    │                     └──────┬───────┘            └───────────────┘
└─────────────┘                            │
                                            │ SQL
                                            ▼
                                    ┌───────────────┐         ┌──────────────────┐
                                    │  MS SQL Server │         │  Вчасно.Каса API  │
                                    │  (таблиця      │◄───────►│  (фіскалізація    │
                                    │   Store і всі  │  HTTPS  │   чеків)          │
                                    │   інші)        │         └──────────────────┘
                                    └───────────────┘
```

- **Фронтенд** — те, що бачить покупець на екрані кіоску: каталог, кошик, оплата. Це статичний сайт (React), зібраний один раз при `docker compose up --build`, роздається через nginx на порту 80.
- **Бекенд** — "мозок" системи: приймає запити фронтенду, спілкується з POS-терміналом (по TCP), пише в базу даних, ставить чеки в чергу фіскалізації, шле листи.
- **База даних (MS SQL)** стоїть на самому Windows-комп'ютері (не в Docker) — так простіше робити бекапи штатними засобами SSMS.
- **POS-термінал** — фізичний пристрій прийому карток, підключений в ту саму локальну мережу, що й комп'ютер кіоску.
- **Вчасно.Каса** — зовнішній хмарний сервіс фіскалізації чеків (реєстрація в ДПС). Бекенд відправляє туди дані про кожен продаж.

## 6. Екран конфігу

### 6.1 Що це і навіщо

Екран конфігу (`/#/setup`) — адміністративний екран для налаштування магазину: назва/адреса, банк-термінал (IP, порт), мерчанти, токени фіскалізації Вчасно.Каса. Це НЕ частина звичайного покупательського інтерфейсу.

### 6.2 Як потрапити на екран конфігу

Є **три** способи, і всі вимагають ввести пароль (окрім першого пункту — там кіоск сам ще не готовий працювати):

1. **Автоматично при першому запуску.** Якщо в БД не вистачає обов'язкових даних (банк не обрано, IP терміналу не вказано, немає токена Вчасно.Каса) — при відкритті `http://localhost` кіоск сам перекине на екран конфігу, без пароля (логічно: показувати покупцю порожній кіоск однаково не можна).

2. **Через сканування спеціального штрихкоду.** Значення штрихкоду задається змінною `VITE_CONFIG_BARCODE` у `docker-compose.yml` (за замовчуванням `09090909090909` — 14 цифр, спеціально не збігається з довжиною реальних товарних EAN-13, які завжди 13 цифр, тож випадково "спрацювати" від сканування звичайного товару неможливо). Треба роздрукувати цей штрихкод на аркуші й тримати в закритому від покупців місці (у сервісній шухляді, у технічного персоналу). Скан → одразу з'являється вікно з проханням ввести пароль.

3. **Через шестерню в режимі "Технічні роботи".** Якщо кіоск переведено в режим "Технічні роботи" (це відбувається автоматично, коли бекенд виявляє розбіжність ЄДРПОУ/назви фірми між налаштуваннями і даними у Вчасно — запобіжник від помилкової фіскалізації), у правому верхньому куті з'являється маленька непомітна шестерня. Клік по ній → те саме вікно з паролем.

**Пароль** — це технічний (сервісний) пароль, окремий від пароля входу в кіоск. Зберігається у таблиці `ServiceUsers` (хешовано, bcrypt). За замовчуванням при першому запуску системи автоматично створюється сервісний користувач з паролем **`123456`**. Пароль можна ввести або вручну на цифровій клавіатурі на екрані, або скануванням цифрового штрихкода (сканер працює як клавіатура — і цифри, і Enter розпізнаються автоматично).

> Пряме відкриття URL `http://localhost/#/setup` в адресному рядку теж вимагає пароль — обійти цю вимогу неможливо, вона перевіряється на самому екрані, а не лише в кнопці входу.

### 6.3 Як змінити сервісний пароль

Через SSMS:
```sql
-- Дізнатись поточних сервісних користувачів
SELECT id FROM ServiceUsers;

-- Створити новий bcrypt-хеш пароля так само, як для пароля магазину (крок 3.5),
-- потім:
UPDATE ServiceUsers SET password = '$2b$10$...' WHERE id = 1;
```

### 6.4 Звідки екран бере дані і як їх зберігає

Екран конфігу — звичайна адмін-панель: при відкритті робить `GET`-запити, при збереженні — `PATCH`/`POST`/`PUT`. Дані живуть у трьох таблицях БД:

| Таблиця | За що відповідає | Через який ендпоінт редагується |
|---|---|---|
| `Store` | назва/адреса магазину, обраний банк, призначені мерчанти, email-адреси | `PATCH /api/setup/store`, `POST /api/setup/assign-merchants` |
| `TerminalConfig` | IP, порт, TID термінала (окремий рядок на кожен банк) | `PUT /api/setup/terminal/:bank` |
| `FiscalConfig` | токен Вчасно.Каса, ЄДРПОУ/ІПН, код податкової групи (taxgrp) — окремий рядок на кожного мерчанта | `PUT /api/setup/fiscal/:merchantId` |

При завантаженні екрана фронтенд викликає `GET /api/setup` (повний знімок усіх трьох таблиць) та `GET /api/setup/kiosk-config` (той самий знімок, але вже "зібраний" — з живою перевіркою токена через Вчасно API, щоб показати, чи збігається ЄДРПОУ/назва фірми в вашому конфізі з тим, що зареєстровано у Вчасно).

Кожна картка на екрані зберігається окремою кнопкою "Зберегти" — тобто можна зберігати частинами, не обов'язково заповнювати все одразу. Є також кнопка **"Перевірити зв'язок"** біля картки терміналу — вона реально стукається до фізичного терміналу по мережі (`POST /api/setup/terminal/:bank/check`) і, якщо термінал відповів, автоматично підтягує список мерчантів з нього — не треба вводити ID мерчанта вручну.

Після заповнення всіх обов'язкових полів внизу з'являється чеклист готовності і кнопка **"🚀 Запустити кіоск"** — вона активна лише коли все обов'язкове заповнено, і просто перенаправляє на головний екран (`/`).

### 6.5 Обов'язкові поля для запуску (readiness-перевірка)

`GET /api/setup/ready` перевіряє мінімальний набір, без якого кіоск НЕ буде продавати:
- Обрано активний банк (`active_bank`)
- Для цього банку є IP і порт термінала
- Призначено основного мерчанта (`default_merchant`)
- Для основного мерчанта є токен Вчасно.Каса
- Якщо є VAT-мерчант — для нього теж потрібен токен

Усе інше (email-адреси, скрінсейвер, акції) — необов'язкове, кіоск працюватиме і без них.

## 7. Екран "Налаштування акцій"

Доступний з екрана конфігу — кнопка **"🏷️ Налаштування акцій"** у шапці (веде на `/#/setup/sales`, так само захищений паролем).

### 7.1 Що таке "акції" тут

Це НЕ окрема таблиця промо-кампаній, а таблиця `Sales` — довідник **типів знижок**, які прив'язуються до конкретного товару через поле `Products.sale_id`. У кожного товару може бути одна "акція" (0 = без акції). Станом на зараз у довіднику 9 записів:

| `sale_custom_id` | Назва | Логіка |
|---|---|---|
| 0 | акція не застосовується | без знижки |
| 1 | знижка | товар, що швидко псується, **не повертається**; знижка росте по мірі наближення терміну придатності (3 рівні: `sale_discount_1/2/3`) |
| 2 | знижка | те саме, але товар **повертається** |
| 3 | новинка | акція для нових товарів, фіксована знижка `sale_discount_1` |
| 4 | знижка | для товарів, що довго не продаються |
| 6 | товар дня | фіксована знижка на визначені товари |
| 7 | комбо | акція для парних товарів (наприклад, "купи хліб — отримай масло дешевше") |
| 8 | дубль | знижка на другий такий самий товар |
| 9 | знижка | знижка на цілу категорію/підкатегорію в магазині — саме той запис, що показується на заставці ("Акція дня", керується через `POST /api/config/store-sale`) |

### 7.2 Активація / деактивація

У кожного запису є перемикач **Активна / Вимкнена** (поле `is_active` в БД, за замовчуванням `true` для всіх). Клік по тумблеру одразу зберігається (`PATCH /api/sales/:id/status`, body: `{ "is_active": true | false }`).

> Важливо: сам факт "вимкнення" акції в цьому довіднику наразі **не приховує автоматично** знижку у товарів, яким вона вже присвоєна на фронтенді (`sale_id` у товару лишається як є) — це довідник-перемикач для майбутньої логіки; поточна функціональність — перегляд і зберігання статусу. Якщо потрібно прибрати знижку з конкретних товарів — редагуйте `sale_id` самих товарів через `POST /api/products/update`.

## 8. Черга фіскалізації

### 8.1 Навіщо потрібна черга

Кожен успішний продаж має бути зареєстрований (фіскалізований) у Вчасно.Каса. Це робиться **не одразу під час оплати**, а через асинхронну чергу — щоб оплата покупця не блокувалась, поки йде спілкування із зовнішнім сервісом фіскалізації, і щоб тимчасова недоступність Вчасно.Каса не ламала касовий процес.

### 8.2 Як влаштована черга

- Таблиця `FiscalQueue`. Кожен рядок = один чек, що чекає (або вже пройшов) фіскалізацію.
- Обробка запускається **кожні 10 секунд** (фоновий процес усередині бекенду, `@Cron`).
- Черга розбита на **незалежні потоки** за комбінацією (банк, мерчант, з ПДВ / без ПДВ). Тобто якщо у вас два мерчанти (без ПДВ і з ПДВ), це фактично дві повністю окремі черги — застрягання однієї не блокує іншу.
- **Хронологічний порядок гарантується лише всередині одного потоку** (одного мерчанта): наступний чек цього мерчанта не почне оброблятись, поки попередній не завершився успіхом або остаточним провалом. Це вимога самого Вчасно.Каса.
- При помилці — повтор з експоненційною затримкою: 10с → 20с → 40с → ... до максимум 30 хв між спробами. Максимум **10 спроб**.
- Якщо Вчасно повертає `res_action = 3` — це "фатальна" помилка (наприклад, зміна не відкрита, картка каси заблокована) — повторювати немає сенсу, чек одразу переходить у статус `failed`, і на `alert_email`/`MAIL_TO` летить лист з проханням розібратись вручну в кабінеті Вчасно.Каса.
- Якщо звичайних 10 спроб не вистачило — чек теж переходить у `failed` і теж шле лист.
- Виправлений вручну чек (усунули причину в кабінеті Вчасно) можна повернути в роботу: `UPDATE FiscalQueue SET status = 'pending', attempts = 0 WHERE id = ...`.

### 8.3 Статуси чека в черзі

| Статус | Що означає |
|---|---|
| `pending` | чекає своєї черги (або в затримці backoff) |
| `processing` | зараз обробляється (звичайно кілька секунд) |
| `completed` | успішно фіскалізовано |
| `failed` | всі спроби вичерпано АБО фатальна помилка — потребує ручного втручання |

### 8.4 "Протерміновані" чеки (нічне архівування)

**Щодня о 00:00 за Києвом** усі чеки попереднього дня, що ще не отримали статус `completed` (тобто `pending`, `processing` або `failed`), автоматично переносяться з `FiscalQueue` в архівну таблицю `OverdueFiscalQueue`, і чергу на новий день "очищають" — це запобігає тому, щоб застряглий чек учорашнього дня назавжди блокував потік. Список перенесених чеків одразу надсилається на email у вигляді XLSX-файлу (див. [розділ 9.1](#91-звіт-про-протерміновані-чеки)).

### 8.5 Попередження про переповнення черги

Якщо задано `FISCAL_QUEUE_ALERT_THRESHOLD` (кількість) — і в черзі накопичилось `pending`+`processing` чеків більше за цей поріг, надсилається email-попередження (не частіше 1 разу на годину, щоб не заспамити). За замовчуванням `0` = вимкнено.

### 8.6 Де подивитись стан черги

- `GET /api/fiscal/queue/pending` — скільки зараз чеків очікує/обробляється (просто число).
- `GET /api/fiscal/queue/failed` — список чеків, що остаточно не пройшли, з текстом помилки.
- Напряму в SSMS: `SELECT * FROM FiscalQueue WHERE status != 'completed' ORDER BY created_at;`

## 9. Автоматичні звіти

Усі звіти надсилаються поштою, налаштування SMTP береться з таблиці `Store` (поля `mail_*`), а при першому старті бекенду автоматично підтягується з `docker-compose.yml` (`MAIL_*`), якщо в БД ще порожньо — див. [розділ 10.7](#107-як-змінити-email-налаштування).

### 9.1 Звіт про протерміновані чеки

- Коли: щодня о **00:00 (Київ)**, разом з нічним архівуванням (розділ 8.4). Якщо протермінованих чеків немає — лист не надсилається.
- Кому: на адресу з `Store.alert_email` (заповнюється з env `MAIL_TO` при першому старті).
- Формат: Excel (.xlsx), колонки — ID, дата створення, банк, мерчант, з ПДВ чи ні, статус, кількість спроб, текст останньої помилки, ID товарів.

### 9.2 Звіт по оцінках покупців (feedback)

- На виході з покупки/на екрані кіоску покупець може лишити оцінку 1–5 (`POST /api/feedback`) — записується в таблицю `Feedbacks`.
- Звіт формується щодня о **01:00**, надсилається на `Store.feedback_email`, якщо ця адреса заповнена. Якщо за минулу добу оцінок не було — лист не надсилається.
- Вміст: загальна кількість оцінок, середній бал, розподіл по кожній оцінці (скільки 5★, 4★ ... 1★, у відсотках).
- Захист від дублю: дата останньої відправки зберігається в `Store.last_feedback_report_date` — навіть якщо бекенд перезапуститься кілька разів за день, повторний лист за той самий день не піде.

### 9.3 Фінансовий звіт (за запитом)

На відміну від двох попередніх, цей звіт **не автоматичний** — його треба запросити вручну через `POST /api/finance` за потрібний період (детальніше [розділ 22](#22-admin-finance-kiosk-sync-static-files)).

### 9.4 Сповіщення про помилки (не звіти, а алерти)

- Фатальна помилка фіскалізації (`res_action=3`) — лист одразу.
- Остаточний провал чека після 10 спроб — лист одразу.
- Переповнення черги — лист (не частіше 1/год).
- Розбіжність ЄДРПОУ/назви фірми між вашим конфігом і Вчасно (могли неправильно ввести токен/дані) — лист на `OVERDUE_FISCALS_EMAIL`, і кіоск переходить у режим "Технічні роботи" до виправлення.

## 10. Типові завдання підтримки

### 10.1 Додати новий товар

`POST /api/products/add` (масив, можна кілька товарів за раз). Обов'язкові поля: `product_name`, `product_code`, `barcode`, `measure`, `product_name_ua`, `product_category`, `product_subcategory`, `product_left` (залишок), `product_price`, `exposition_term`, `sale_id`. Категорія й підкатегорія мають вже існувати в БД (інакше товар потрапить у `invalidCategory` у відповіді й не додасться). Товар потрапляє не одразу в продаж, а в чергу (`ProductUpdateQueue`) — застосовується, коли кіоск переходить у режим очікування (idle), щоб не переривати покупця посеред покупки; якщо кіоск вже в idle на момент запиту — синхронізація запускається негайно.

### 10.2 Змінити ціну / залишок товару

`POST /api/products/update`, обов'язково — `barcode`, решта полів (ціна, залишок через списання, назва тощо) — лише ті, що змінюються.

Списати частину залишку (наприклад, товар зіпсувався): `POST /api/products/withdraw`, `[{ "barcode": "...", "quantity": 2 }]`.

Повна інвентаризація (списати геть усе): `POST /api/products/inventarization` — без тіла запиту, обнуляє залишки всіх товарів. **Використовувати обережно.**

### 10.3 Додати категорію / підкатегорію

`POST /api/config/category` → потім `POST /api/config/subcategory` (підкатегорія прив'язується до вже існуючої категорії за `cat_1C_id`). Дублікати `cat_1C_id`/`subcat_1C_id` система відхилить з поясненням помилки.

### 10.4 Встановити "акцію дня" (банер на заставці простою)

`POST /api/config/store-sale` — вказати категорію+підкатегорію, назву, заголовок, розмір знижки у %. Ця акція показується на заставці (idle-екрані) кіоску як карусель товарів зі знижкою.

### 10.5 Скрінсейвер (заставка)

1. Завантажити файл: `POST /api/screensaver/upload` (form-data, поле `file`; зображення до `.jpg/.jpeg/.png/.webp/.gif`, відео `.mp4/.webm/.mov`, до 200 МБ).
2. Активувати: `POST /api/screensaver/config`:
   - Один статичний банер: `{ "mode": "static", "filename": "promo.jpg" }`
   - Карусель усіх завантажених зображень: `{ "mode": "carousel", "interval": 20 }`
   - Відео: `{ "mode": "video", "filename": "ad.mp4" }`
3. Прибрати — повернутись до стандартної CSS-заставки: `DELETE /api/screensaver/config`.

### 10.6 Змінити пароль входу в кіоск / сервісний пароль

Див. [3.5](#35-логін-у-фронтенд-пароль-магазину) (пароль магазину) і [6.3](#63-як-змінити-сервісний-пароль) (сервісний пароль екрана конфігу).

### 10.7 Як змінити email-налаштування

Через екран конфігу (картка "Магазин") — три поля: email для сповіщень про помилки фіскалізації, email техпідтримки, email для щоденного звіту по оцінках. Технічні SMTP-налаштування (сервер, порт, логін/пароль поштової скриньки) редагуються напряму в БД (таблиця `Store`, колонки `mail_host`, `mail_port`, `mail_secure`, `mail_user`, `mail_pass`, `mail_from`) — на екрані конфігу форми для них поки немає, і зміна набуде чинності лише після **перезапуску бекенду** (`docker compose restart backend`), бо конфіг пошти читається з БД лише один раз при старті.

### 10.9 Ручна синхронізація черги товарів/категорій

Якщо потрібно негайно "протолкнути" накопичені в чергах зміни (замість очікування, поки кіоск сам піде в режим очікування): `POST /api/admin/kiosk/sync`.

## 11. Усунення несправностей

| Симптом | Що перевірити |
|---|---|
| `docker compose ps` не показує `backend` як `Up` | `docker compose logs backend --tail=100` — зазвичай помилка підключення до БД (перевірити крок 1.1–1.2) або зайнятий порт 6006 (`netstat -ano \| findstr :6006`) |
| У логах `unable to open tcp connection` / `Login failed for user 'mm_user'` | SQL Server не в змішаному режимі автентифікації (крок 1.1), або пароль користувача не збігається з `DATABASE_URL` |
| Кіоск завис на "Завантаження..." на екрані конфігу | Перевірити, чи `backend` відповідає: `curl http://localhost:6006/api/setup/ready` з того ж комп'ютера |
| Термінал показує "офлайн" на екрані конфігу | Перевірити фізичне з'єднання термінала з мережею, правильність IP/порту (`CLIENT_HOST`/`CLIENT_PORT` у `docker-compose.yml` АБО поле в `TerminalConfig`, якщо міняли через екран), чи термінал не "спить" (термінали MonoBank іноді засинають, прокидання до 15с — це нормально) |
| Оплата проходить, але чек не з'являється / статус `failed` у черзі | `GET /api/fiscal/queue/failed` — подивитись текст помилки; часто причина — не відкрита зміна в РРО або протермінований токен Вчасно.Каса |
| Кіоск раптом показує "Технічні роботи" всім покупцям | Ознака розбіжності даних мерчанта з Вчасно (розділ 9.4) — перевірити ЄДРПОУ/назву фірми в `FiscalConfig` проти кабінету Вчасно.Каса, виправити через екран конфігу → картку мерчанта — при збереженні коректних даних режим знімається автоматично |
| Не приходять email-сповіщення/звіти | Перевірити `Store.mail_*` заповнені (розділ 10.7), лист не потрапив у спам, SMTP-акаунт не заблокував відправку через незнайомий IP (типово для ukr.net при першому підключенні з нового сервера) |
| Зображення товару/категорії не відображається | Перевірити, що bind-mount `C:/git/mm-images:/app/images` існує і в ньому є файл; права доступу папки |
| Chrome не відкрився після перезавантаження | Перевірити Task Scheduler (крок 4.2) — статус останнього запуску завдання; переконатись, що Docker Desktop встиг піднятись за 1 хв (за потреби збільшити затримку) |

## 13. Auth

### `POST /api/auth/store/login`

Масив об'єктів. Приклад одного елемента:

```json
  "product_left": 10,
  "product_price": 45.5,
  "exposition_term": 5,
  "sale_id": 0,
  "product_category": 1,
  "product_subcategory": 2,
  "is_VAT_Excise": false,
  "excise_product": false
}
```
| Поле | Обов'язкове |
|---|:---:|
| `product_name`, `product_code`, `barcode`, `measure`, `product_name_ua`, `product_category`, `product_subcategory`, `product_left`, `product_price`, `exposition_term`, `sale_id` | ✅ |
| `child_product_barcode` | ✅ лише якщо `sale_id === 7` (комбо) |
| `product_name_ru`, `product_description`, `product_image`, `is_VAT_Excise`, `excise_product`, `combo_id`, `is_new_product`, `product_division` | — |

**Response** повертає деталізацію: `queued` (скільки прийнято), `missingFields`, `invalidCategory`, `failedToConvert`, `constraintViolations` (barcode/product_code конфліктує з уже існуючим).

### `POST /api/products/update`
Масив, обов'язково лише `barcode` у кожному елементі + будь-які поля зі списку `ALLOWED_UPDATE_KEYS`: `product_name`, `product_code`, `measure`, `product_name_ru`, `product_name_ua`, `product_description`, `product_image`, `product_price`, `product_discount`, `exposition_term`, `sale_id`, `discount_price_1/2/3`, `combo_id`, `product_category`, `product_subcategory`, `is_VAT_Excise`, `excise_product`, `is_new_product`, `product_division`. Будь-яке ІНШЕ поле — запис буде відхилено з поясненням `Forbidden keys`. Якщо товару з таким `barcode` ще немає — `product_category`+`product_subcategory` стають обов'язковими (створення нового товару).

### `POST /api/products/withdraw`
```json
[{ "barcode": "4820000000017", "quantity": 2, "limit": "" }]
```
`barcode`, `quantity` — обов'язково; `limit` — необов'язково.

### `POST /api/products/inventarization`
Без тіла. Списує залишки **усіх** товарів у нуль.

### `POST /api/products/image`
```json
[{ "productImage": "<base64>", "fileName": "4820000000017.jpg" }]
```
Обидва поля обов'язкові. Ім'я файлу без розширення має збігатись з `barcode` товару.
