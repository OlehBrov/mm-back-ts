# Акції та знижки — довідник

Інструкція по системі акцій/знижок кіоску MicroMarket, **актуальна після переходу на бекенд-авторитетне ціноутворення** (`PricingService`). Якщо десь бачите стару версію цього файлу або згадки "рахує фронтенд" — це неактуально, все нижче описує поточний стан.

## 1. Головний принцип

Усе ціноутворення рахує **бекенд**, і тільки бекенд (`PricingService`, `src/modules/pricing/pricing.service.ts`). Фронтенд ніколи сам не рахує знижку — він або отримує вже пораховану ціну в відповіді на `GET /api/products`, або замовляє "живий" перерахунок кошика через `POST /api/cart/price`. Фінальний продаж (`POST /api/cart/sell`) теж повністю перераховується на бекенді — що б не надіслав фронтенд, ціна й знижка беруться з БД, а не з тіла запиту.

Практичний наслідок: **щоб змінити знижку покупцю, досить змінити дані в БД** (через відповідний ендпоінт) — переробляти фронтенд не треба, він завжди показує актуальний розрахунок.

## 2. Рівні, на яких можна дати знижку

### 2.1 Рівень товару (`Products.sale_id`)

Товару присвоюється `sale_id`, що посилається на рядок довідника `Sales` (`Sales.sale_custom_id`). Це основний механізм. Типи:

| `sale_id` | Назва | Як рахується | Де діє |
|---:|---|---|---|
| `0` | без акції | — | — |
| `1` | скоропорт, не повертається | 3 рівні знижки за днями до кінця терміну придатності (`sale_discount_1` за 3 дні, `_2` за 2 дні, `_3` — менше 2 днів) | товар у каталозі |
| `2` | скоропорт, повертається | те саме, що `1` | товар у каталозі |
| `3` | новинка | фіксовано `sale_discount_1` | товар у каталозі |
| `4` | довго не продається | фіксовано `sale_discount_1` | товар у каталозі |
| `6` | товар дня | фіксовано `sale_discount_1` | товар у каталозі |
| `7` | комбо | `sale_discount_1` на обидва товари пари, **лише коли обидва в кошику** | кошик (рівень пари) |
| `8` | дубль | `sale_discount_1` на кожну 2-гу одиницю **того самого** товару в кошику | кошик (рівень кількості) |
| `9` | "акція дня" (категорія/підкатегорія) | фіксовано `sale_discount_1`; призначається масово через окремий механізм — [2.4](#24-рівень-магазину-акція-дня) | товар у каталозі |
| `10` | мінімальний чек | `sale_discount_1` на всі товари **без власної акції**, коли сума кошика сягає `Sales.threshold_amount` | кошик (рівень усього чека) |

**Як присвоїти:**
```json
POST /api/products/update
[{ "barcode": "4820000000017", "sale_id": 3 }]
```
`sale_id: 0` знімає акцію з товару. Бекенд **перевіряє, що такий `sale_id` дійсно існує в `Sales`** — якщо ні, товар відхиляється з поясненням у відповіді (`rejected` / `invalidSaleId`), у БД нічого не змінюється.

### 2.2 Комбо (`sale_id = 7`) — пара товарів

Комбо — це коли один товар (наприклад, кава) продається зі знижкою разом з іншим (наприклад, круасан). Технічно: `Products.combo_id` пов'язує основний товар із дочірнім через таблицю `ComboProducts`.

**Створити комбо можна тільки через `POST /api/products/add`:**
```json
{
  "barcode": "4820000000017",
  "sale_id": 7,
  "child_product_barcode": "4820000000024",
  ...інші обов'язкові поля товару...
}
```
⚠️ **`PATCH /api/products/update` НЕ підтримує зміну пари** (поле `child_product_barcode` там ігнорується) — тобто змінити чи прибрати вже створену пару можна тільки повторним `POST /api/products/add` тим самим штрихкодом, або напряму в БД. Якщо це потрібно частіше — варто окремо доробити підтримку в `update`.

Якщо дочірній товар закінчився на складі — бекенд сам ховає бейдж і знижку (перевіряється "наживо" при кожному запиті), пару вручну розбирати не треба.

### 2.3 Дубль (`sale_id = 8`)

Проста фіксована знижка на кожну другу одиницю того самого товару. Присвоюється так само, як звичайний `sale_id`:
```json
POST /api/products/update
[{ "barcode": "4820000000017", "sale_id": 8 }]
```
Розрахунок відбувається лише на рівні кошика (`POST /api/cart/price`, `POST /api/cart/sell`) — окрема ціна "за штуку" в каталозі для товару з `sale_id=8` не показує знижку, бейдж показується, а сама знижка з'являється, коли покупець кладе в кошик ≥2 шт.

### 2.4 Рівень магазину ("акція дня")

Масова знижка на **всю категорію або підкатегорію одразу** — та, що видно на заставці кіоска.

```json
POST /api/config/store-sale
{
  "store_sale_product_category": 1,
  "store_sale_product_subcategory": 2,
  "store_sale_name": "Літній розпродаж",
  "store_sale_title": "Знижка 20%",
  "store_sale_discount": 0.2
}
```
Усі поля обов'язкові, `store_sale_discount` — дріб (0.2 = 20%), категорія/підкатегорія мають вже існувати.

Що відбувається при застосуванні (в idle-момент, див. [розділ 4](#4-черга-і-мить-застосування)):
- оновлюється `Store.store_sale_*`;
- оновлюється сам довідник `Sales` (`sale_custom_id=9`: назва + `sale_discount_1`);
- **усім товарам** обраної категорії/підкатегорії ставиться `sale_id = 9` — і **скидається `combo_id`**, якщо товар був частиною комбо (побічний ефект, майте на увазі).

Подивитись поточну "акцію дня": `GET /api/config/store-sale`.

Прямого "вимкнути акцію дня" ендпоінта немає — практично: викликати той самий `POST` з `store_sale_discount: 0`, або вручну в БД прибрати `sale_id=9` у відповідних товарів.

### 2.5 Рівень категорії / підкатегорії (`category_discount` / `subcategory_discount`)

⚠️ Це **не те саме**, що "акція дня" з п. 2.4. Це фонова знижка "за замовчуванням" — застосовується автоматично до товару, **якщо в нього немає власного `sale_id`** (тобто `sale_id=0` або поточний тип неактивний/поза вікном дії). Пріоритет: власний `sale_id` товару → знижка підкатегорії → знижка категорії → нічого.

```json
// на категорію
POST /api/config/category
[{ "category_name": "Напої", "cat_1C_id": 100, "category_discount": 0.1 }]
PATCH /api/config/category
[{ "cat_1C_id": 100, "category_discount": 0.15 }]

// на підкатегорію
POST /api/config/subcategory
[{ "cat_1C_id": 100, "subcat_1C_id": 200, "subcategory_name": "Соки", "subcategory_discount": 0.1 }]
PATCH /api/config/subcategory
[{ "cat_1C_id": 100, "subcat_1C_id": 200, "subcategory_discount": 0.05 }]
```
На бейджі товару це показується як синтетичний тип (не справжній `sale_id`) з підписом "Знижка категорії"/"Знижка підкатегорії".

### 2.6 Знижка по всій корзині (мінімальний чек, `sale_id = 10`)

Єдина "загальнокошикова" акція. Не присвоюється товарам — це властивість самого типу `Sales` із `sale_custom_id = 10`:

```json
POST /api/setup/sales/edit   (або /api/sales/edit для 1С — див. розділ 3)
{ "sale_custom_id": 10, "sale_discount_1": 0.1, "threshold_amount": 500 }
```
Коли сума кошика (до цієї знижки) сягає `threshold_amount`, усі товари в кошику, які **не мають жодної іншої знижки**, отримують додатково `sale_discount_1`. Керується виключно через `Sales` (розділ 3) — окремого ендпоінта для порогу немає.

## 3. Довідник `Sales` — керування типами акцій

Є **два набори ендпоінтів** для однієї й тієї ж таблиці `Sales` — різняться лише тим, коли застосовується зміна (розділ [4](#4-черга-і-мить-застосування)):

| Дія | Ендпоінт для 1С (у чергу) | Ендпоінт для екрана `/setup/sales` (миттєво) | Тіло |
|---|---|---|---|
| Список усіх типів | `GET /api/sales` | `GET /api/sales` (спільний, лише читання) | — |
| Додати новий тип | `POST /api/sales/add` | `POST /api/setup/sales/add` | `{ sale_name, sale_custom_id, sale_discount_1?, sale_discount_2?, sale_discount_3?, sale_description?, threshold_amount? }` |
| Редагувати тип | `POST /api/sales/edit` | `POST /api/setup/sales/edit` | `{ sale_custom_id, ...будь-які поля вище, is_active? }` |
| Увімкнути/вимкнути тип | `PATCH /api/sales/:saleCustomId/status` | `PATCH /api/setup/sales/:saleCustomId/status` | `{ is_active: boolean }` |
| Видалити тип | `DELETE /api/sales/delete` | `DELETE /api/setup/sales/delete` | `{ sale_custom_id }` |

Екран кіоску "Налаштування акцій" (`SalesSettingsScreen.tsx`) викликає **лише** `/api/setup/sales/*` — редагування ставок знижки (для типів 1/2 — усі три рівні, для решти — одна ставка) і порогу суми чека (для `sale_custom_id=10`) вже є в інтерфейсі, разом з тумблером увімкнути/вимкнути.

### `is_active = false` — повністю вимикає тип

На відміну від старої версії системи, зараз перемикач `is_active` **реально вимикає акцію на кіоску**: товар з таким `sale_id` поводиться так, ніби акції в нього нема (з fallback на знижку категорії/підкатегорії, якщо є), дубль і комбо на рівні кошика теж перестають рахуватись, а поріг чека (`sale_custom_id=10`) просто не спрацьовує. Перевірено в `PricingService` — гейт стоїть у кожному з чотирьох місць розрахунку.

## 4. Черга і мить застосування

Тут `Sales` відрізняється від товарів/категорій наявністю **двох джерел змін** із різними гарантіями:

- **`/api/sales/*`** — цей шлях може викликати 1С (чи інший зовнішній інструмент) **у будь-який момент**, незалежно від того, що зараз на екрані кіоску. Тому зміни тут спершу записуються в чергу (`SaleTaskQueue`) і застосовуються бекендом лише коли кіоск переходить у стан очікування (заставка/idle) — щоб ціна не "стрибала" прямо під час того, як покупець дивиться на товар чи стоїть у кошику. Запит повертає `200 OK` одразу ("queued for deferred idle sync"), але ефект з'явиться щойно кіоск звільниться (або миттєво, якщо він уже вільний у момент запиту).
- **`/api/setup/sales/*`** — цей шлях доступний лише з екрана `/setup/sales`, який замінює собою весь інтерфейс покупки на тому ж екрані кіоску. Поки він відкритий, покупець фізично не може одночасно оформлювати покупку — тому ризику "ціна змінилась під час покупки" тут немає, і зміна застосовується **одразу**, без черги.

Примусово прогнати чергу товарів/категорій (для тестів): `POST /api/admin/kiosk/sync`.

## 5. Сповіщення фронтенду (socket)

Бекенд надсилає через WebSocket:
- `product-updated` — після зміни товару, категорії/підкатегорії, або типу акції в `Sales` (усе, що описано в розділах 2–3). Фронтенд ловить цю подію й одразу перезапитує список товарів — покупець бачить оновлені ціни й бейджі без ручного оновлення сторінки. Для `/api/sales/*` (чергове) — надсилається щойно чергу оброблено (idle-момент); для `/api/setup/sales/*` (миттєве) — одразу в відповідь на запит.
- `store-sale-updated` — додатково після зміни "акції дня" (розділ 2.4).

Покрито для всіх шляхів зміни: `/api/products/add`, `/api/products/update`, `/api/config/category(+PATCH)`, `/api/config/subcategory(+PATCH)`, `/api/config/store-sale`, `/api/sales/*` та `/api/setup/sales/*`.

## 6. Відомі обмеження

- Змінити чи прибрати пару комбо для **вже існуючого** товару можна лише повторним `POST /api/products/add`, не через `update` (розділ [2.2](#22-комбо-sale_id--7--пара-товарів)).
- Ендпоінти `/api/sales/*`, `/api/setup/sales/*` і `/api/config/*` не захищені авторизацією (як і раніше) — це не змінювалось у цьому доопрацюванні.
